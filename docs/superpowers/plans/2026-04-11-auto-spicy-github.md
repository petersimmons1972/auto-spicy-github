## Step 4: Prose Pass

Rewrite each doc page. Rules:

- Entertaining, example-rich, 2nd-person where natural
- Match the voice and personality defined in `VISUAL-IDENTITY.md`
- No passive voice. No filler phrases ("This document explains...", "In order to...")
- Every code example must be real and runnable — no pseudocode
- Every flag and option in CLI docs must have an example invocation
- Narrative/philosophy pages: write with genuine voice and concrete specifics
- Technical reference pages (CLI, architecture): prioritize accuracy and scannability over prose

**Splitting long pages:**

For any page flagged "SPLIT" in the audit:
1. Identify natural topic breaks (## headings or logical groupings)
2. Create one sub-page per topic under `docs/[topic-name].md`
3. Replace the original page content with a navigation hub:
   - 1–2 sentence summary of each sub-page
   - Link to each sub-page
   - Keep any essential overview content (first 100 lines or so)
4. The original file becomes the index — it should be short and scannable

Example: a 600-line `README.md` with sections Installation, Configuration, CLI Reference, Architecture, FAQ becomes:
- `README.md` (80-line navigation hub)
- `docs/installation.md`
- `docs/configuration.md`
- `docs/cli-reference.md`
- `docs/architecture.md`
- `docs/faq.md`

## Step 6: Artwork (fetch from web)

For each page requiring artwork: search for and fetch a public domain image that fits the page's theme and the repo's visual identity from `VISUAL-IDENTITY.md`. Commit it to `docs/assets/posters/` and replace the `<!-- VISUAL: -->` placeholder with a real image reference.

### Search strategy

Use WebSearch to find images. Preferred sources (all have strong public domain collections):

- **Wikimedia Commons** — `site:commons.wikimedia.org [subject]`
- **Library of Congress** — `site:loc.gov/resource [subject]`
- **National Archives** — `site:catalog.archives.gov [subject]`
- **Europeana** — `site:europeana.eu [subject]`

### License verification

Before fetching, confirm the image is:
- Public domain (pre-1928, US government work, or explicitly marked PD)
- Or CC0 / Creative Commons with no restrictions

### Fetch and commit

1. WebFetch the direct image URL (full resolution, `.jpg` or `.png`)
2. Save to `docs/assets/posters/[page-slug].jpg`
3. Replace `<!-- VISUAL: ... -->` in the doc with:
   ```markdown
   ![Caption](assets/posters/[page-slug].jpg)
   *Source: [attribution — title, creator, year, institution]*
   ```

### Matching artwork to the project

Match the artwork subject and period to the project's `VISUAL-IDENTITY.md` imagery style. The visual identity doc tells you what kinds of images suit this project — honor it.

### If no suitable public domain image exists

Fall back to generating a thematic SVG illustration in the repo's visual identity style (using `visual-output-standards` and `VISUAL-IDENTITY.md` palette). Save to `docs/assets/posters/[page-slug].svg`.

# Visual Output Standards

**This is the single source of truth for SVG and chart craft quality.** Every agent producing visual output reads this before touching a pixel. Palette and brand colors come from your project's `docs/assets/VISUAL-IDENTITY.md` — this skill enforces universal craft rules that apply regardless of project aesthetic.

---

## 1. Technical Pre-Flight Rules

These rules MUST be followed for every SVG. They are universally applicable and catch the most common classes of visual failure.

### Font Size

| Context | Minimum |
|---------|---------|
| Chart data labels | 14px |
| Footnotes / source lines | 12px |
| Brand artwork SVGs | 11px at viewBox scale |
| Hero numbers / callouts | 42px |

**Font families:**

Use fonts from your `VISUAL-IDENTITY.md` typography section. If none specified, safe defaults:
- Display: `'Playfair Display', Georgia, serif`
- Body: `Inter, 'Segoe UI', sans-serif`
- Monospace: `'JetBrains Mono', 'Fira Code', monospace`

### Paint Order

Render elements in this sequence — no exceptions:

1. **Backgrounds** (fills, gradient fills)
2. **Geometry** (bars, arcs, polygons, grid lines)
3. **Strokes** (borders, benchmark dashes)
4. **Text** (labels, titles, annotations)

**Critical rule:** Never draw a text element before an opaque fill that overlaps its bounding box. This is the #1 class of bug that code review misses — the code is syntactically correct but the z-order causes occlusion. Verify explicitly after computing layout.

### Geometry on a Horizontal Baseline — Use Upper Semicircles, Not Full Circles

When you need a decorative disc or round motif whose diameter sits ON a horizontal element (a platform bar, a base line, a rule), **build it as upper-semicircle `<path>` arcs, not full `<circle>` elements.**

**Why:** SVG uses a y-down coordinate system. A `<circle cx="600" cy="650" r="45">` drawn before a platform bar at `y=650` will have its upper half above the bar (visible) AND its lower half below the bar (also visible). The result is a disc hanging BELOW the bar. 

**Correct construction:**

```svg
<!-- Upper half-disc sitting on y=650 -->
<path d="M 555,650 A 45,45 0 0 1 645,650 Z" fill="#D4AF37"/>
```

The arc goes from `(x - r, y)` to `(x + r, y)` with `large-arc-flag=0` and `sweep-flag=1`. Clockwise sweep on a y-down canvas produces an arc bulging UPWARD. The `Z` closes the path at the baseline.

**Verify:** After generating the arc, mentally sweep from start to end. On a y-down canvas with sweep-flag=1, clockwise from `(x-r, y)` to `(x+r, y)` is upward.

**Never:** Use a full `<circle>` for any decorative element whose center sits on a horizontal element drawn after it.

### Text Container Margins

Agents cannot measure actual font metrics. All text containers MUST include **25% padding** beyond the estimated text width.

**Text width estimation:**
- Regular text: `font_size * 0.52` px per character
- Bold text: `font_size * 0.62` px per character

If estimated text width exceeds 75% of the container, the text WILL overflow on some browsers. Shrink font, abbreviate, or widen the container.

### SVG Character Set

**ASCII only** in SVG text elements. No Unicode special characters (bullets, arrows, check marks, em dashes). Build visual markers from SVG primitives: `<circle>` for bullets, `<line>` or `<path>` for arrows, `<rect>` + color fill for status indicators.

**Why:** Unicode glyphs render inconsistently across font stacks and browsers.

### Polygon and Geometric Layout

All polygon vertices MUST be computed from a single stated center point. No eyeballed coordinates. If you cannot state the center `(cx, cy)` and the computation for each vertex, the geometry is unverifiable.

### ViewBox and Namespace

Every SVG root element MUST have:
- `viewBox="0 0 [width] [height]"` — defines the coordinate space
- `xmlns="http://www.w3.org/2000/svg"` — required for standalone SVG files
- `width="100%"` — enables responsive scaling in HTML contexts

Standard dimensions:
- Landscape diagram: `viewBox="0 0 750 420"`
- Portrait poster: `viewBox="0 0 512 768"`
- Square icon: `viewBox="0 0 600 600"`

Match viewBox to the context you're rendering in. State the effective rendering width in your plan before writing the SVG.

### Post-Creation Verification Checklist

After generating ANY SVG, verify:
1. All text elements >= minimum font size for the context
2. No opaque fill element occludes a text element drawn earlier
3. All polygons are centered on their stated center point
4. No content rendered outside the viewBox boundary
5. No text truncated at SVG edges (check right and bottom margins)
6. Contrast ratio >= 4.5:1 on all text (WCAG AA)

## 2. Color and Palette

**Your palette comes from `docs/assets/VISUAL-IDENTITY.md`, not from this skill.**

This skill enforces these universal palette rules:

- Use exactly the colors defined in your `VISUAL-IDENTITY.md`. Do not improvise new colors.
- Every color used must have a named role (Primary, Accent, Text, Muted, etc.)
- Contrast ratio >= 4.5:1 on all text against its background (WCAG AA)
- When in doubt whether a color is legible: it probably isn't. Use a higher-contrast alternative.

**Accent color usage:** Accent colors should mark insight and emphasis, not decoration. When an accent color appears, it should mean "pay attention here." Using it for decorative borders or background fills dilutes the signal.

---

## 3. Aesthetic Principles

These separate intentional visual design from generic output. Technical compliance is necessary but not sufficient.

### Data Density

Every pixel earns its place. No decorative gradients, drop shadows, or background textures that don't carry information. A bar chart with 4 bars doesn't need a 1400x800px canvas — it needs a well-framed, smaller canvas.

### Deliberate Whitespace

Margins are intentional framing, not wasted space. Charts that breathe feel authoritative. Charts that fill every pixel feel cluttered.

Minimum recommended margins:
- Top: 50px (title clearance)
- Bottom: 60px (x-axis labels + footnotes)
- Left: 70px (y-axis labels)
- Right: 20px (edge buffer)

### Verdict-First Titles

Every chart title states the finding, not the topic. The title is a sentence, not a label.

| Fails | Passes |
|-------|--------|
| "Capability Comparison" | "Team A Outperforms on Throughput, Team B Wins on Latency" |
| "Performance Over Time" | "Response Time Improved 43% After Cache Layer Added" |
| "User Retention" | "Weekly Active Users Up 28% Since Onboarding Redesign" |

**Metric requirement:** Every verdict-first title should contain at least one specific metric (%, time, count, ratio). A title without a number is an opinion.

### Parity Is Information

When two values are within 10% of each other, the chart MUST either:
1. Display a visible **PARITY** callout explaining WHY the tie matters, OR
2. Be removed and replaced with one sentence.

Silence on a tie is worthless to a reader making a decision.

### Business Value Annotation

Every chart or diagram benefits from a plain-language caption immediately below:

```markdown
![Chart description](assets/svg/chart.svg)
*What this shows: [one sentence about the decision this informs]*
```

The annotation answers: "What should I do differently because of this?" Not "what data does this show."

### Magazine-First Rule

When choosing between visualization approaches, prefer the one that would look at home in a printed magazine. If it looks like a homework assignment, redesign it.

## 4. Chart Dimensions

| Parameter | Value |
|-----------|-------|
| Minimum size | 600×400px |
| Maximum size | 1400×800px |
| Preferred aspect ratio | 1.5:1 to 2:1 |
| Default landscape | 750×420px |
| Default portrait | 512×768px |
| Default margin | 60px (adjust to content) |

Scale the canvas to the content, not the other way around. A 4-bar chart should be ~600×350px, not 1310×620px.

---

## 5. Data Integrity Rules

- Fallback defaults must **fail loud, not silent**. Never use a plausible-looking hardcoded number when data is missing.
- Every missing-data state must produce a visible "DATA MISSING" label or equivalent — not a blank space.
- **Triage by decision impact.** A chart that could mislead a real decision is higher priority than cosmetic issues.

## 6. Artwork Workflow

For illustrations, posters, and visual content:

1. **Before creating:** Read this entire skill. All rules are hard requirements.
2. **State the rendering context** in your plan: target platform, viewBox dimensions, effective rendering width.
3. **Create the artwork** following Sections 1–3 above.
4. **Verify** against the Post-Creation Checklist (Section 1).

3. **Close the issue** referencing the skill update commit
4. **Do NOT store quality rules in conversation history or memory** — rules live here only

This skill grows over time. Every failure makes the next creation better.

# Art Direction — Visual Identity Discovery

This skill runs when `docs/assets/VISUAL-IDENTITY.md` does not exist in the target repo, or when the user explicitly asks to establish or refresh the visual identity.

The goal: author a `VISUAL-IDENTITY.md` that reflects *this project's* personality — not a template, not an imposed style. Two repos using this skill should end up looking completely different if their projects are different.

---

## Step 1: Check for Installed Design Skills

Before running the discovery conversation, check if the user has a design skill installed:

Scan `~/.claude/skills/` for any skill with "design", "ui", "ux", or "visual" in the name or description.

If found, prompt:

> "I found [skill-name] installed. Would you like to use it as your visual design reference? Options:
> - **yes** — use [skill-name] as the design foundation, pull palette and typography from it
> - **no** — I'll ask you questions and build a custom identity from scratch
> - **both** — ask me the questions, then we'll pick specific options from [skill-name] that match your answers"

**Recommended default:** `ui-ux-pro-max` from skills.sh gives access to 50 styles, 21 palettes, and 50 font pairings. It's the recommended starting point if you don't have a strong visual preference. See `docs/design-standards.md` for install instructions.

If no design skill is found, proceed directly to Step 2.

## Step 2: Discovery Conversation

Ask these questions one at a time. Wait for each answer before asking the next. All questions are optional — pressing enter / "skip" / "no preference" is a valid answer.

**Question 1 — Personality:**

> "How should this repo feel? Pick one or more, or describe it in your own words:
>
> - Precise/technical — clean lines, monospace aesthetic, minimal color
> - Warm/accessible — rounded, friendly, inviting
> - Bold/loud — high contrast, commanding, designed to stop you mid-scroll
> - Minimal/professional — restrained palette, lots of whitespace, serious
> - Playful/fun — color, illustration, personality
> - Something else — just describe it"

**Question 2 — Aesthetic reference (optional):**

> "Any era, movement, or visual style that resonates with this project?
>
> Examples: 1920s travel posters, 1980s neon, Bauhaus, Swiss International Style, woodblock prints, technical blueprints, hand-drawn zines, brutalism, Y2K...
>
> Or paste colors/fonts you already like. Or skip this entirely."

**Question 3 — Existing brand materials (optional):**

> "Do you have any existing brand materials for this project? A logo, hex codes, a design system, or a style guide? If so, paste what you have — or describe it."

**Question 4 — Visual references (optional):**

> "Any repos, websites, or docs whose visual design you admire? Even a vague reference ('something like Stripe's docs' or 'warm like Notion but darker') gives me something to work with."

## Step 3: Synthesize and Author VISUAL-IDENTITY.md

Based on the discovery answers, author `docs/assets/VISUAL-IDENTITY.md` using this structure. Every section must be filled with specific, concrete values derived from the answers — no placeholders.

```markdown
# Visual Identity: [REPO NAME]

## Theme
[1-sentence aesthetic statement — what does this repo LOOK like and feel like?]

## Palette
| Role | Hex | Usage |
|------|-----|-------|
| Background | #... | page/chart backgrounds |
| Primary text | #... | headings, key values |
| Secondary text | #... | body text, descriptions |
| Muted | #... | captions, footnotes |
| Accent | #... | highlights, calls to action |
| [Optional: additional roles as needed] | | |

## Typography mood
[serif/sans/mono preference, formal/casual register, weight preferences, letter-spacing]

## Visual personality
[2-3 sentences that describe the aesthetic in concrete terms. Not "clean and modern" — specific. "Industrial precision: right angles, monospace everywhere, nothing decorative unless it's load-bearing."]

## Imagery style
[What kinds of images, illustrations, or artwork suit this project's personality? Be specific about subject matter, period, medium, and mood.]

## SVG constraints
- viewBox: [standard dimensions appropriate to the context — 750x420 landscape is a safe default]
- Corner treatment: [rounded (4-8px radius) / sharp (0px)]
- Gradient style: [radial from center / linear top-to-bottom / flat — no gradients]
- Font family: [primary font with web-safe fallbacks]

## Existing assets
[List any committed SVGs, logos, or posters already in docs/assets/, or "None yet"]
```

**Palette derivation rules:**
- Derive from discovery answers. If the user said "dark and technical" — dark background, high-contrast text, minimal accent.
- If no color preference was given and no design skill is installed, pick a purposeful palette based on the project's domain (dev tool? security? consumer app?) rather than defaulting to generic gray.
- Always include at least 4 color roles: Background, Primary text, Secondary text, Accent.
- Every color must pass WCAG AA contrast (4.5:1) against its background.

## Style Vocabulary (Reference Only)

These historical design styles are vocabulary, not mandates. They exist to help describe aesthetics when users have no other reference point. A project might draw on Cassandre's geometric clarity while using completely different colors and a modern font stack.

| Style | Characteristics | When it fits |
|-------|----------------|--------------|
| **Cassandre (Streamline Moderne)** | Bold geometric shapes, strong diagonals, limited palette, machine-age precision | Geometric, system-heavy, infrastructure, CLI tools |
| **Mucha (Art Nouveau)** | Flowing lines, botanical ornament, warm tones, human-centered | Organic, warm, human-centered projects |
| **Rand (Modernism)** | Grid-based, mark-centric, timeless, reduction to essentials | Professional, corporate, brand systems |
| **Toulouse-Lautrec (Belle Époque)** | Strong silhouettes, flat color, commanding advertising presence | High-impact, bold, event-style projects |
| **Savignac (Mid-century)** | Character-driven, visual humor, warmth, broad appeal | Fun, accessible, community-oriented |
| **Greiman (Digital Modernism)** | Layered information, complex hierarchy, digital-native systems | Data-heavy, UI-heavy, technically complex |

These are starting points for vocabulary. The goal is always a visual identity that feels *right for this specific project* — not a recreation of any historical style.

#!/bin/bash

installed=0
for skill_dir in "$SKILLS_SRC"/*/; do
    if [ -d "$skill_dir" ]; then
        skill_name=$(basename "$skill_dir")
        dest="$SKILLS_DEST/$skill_name"

        if [ -d "$dest" ]; then
            echo "  Updating: $skill_name"
        else
            echo "  Installing: $skill_name"
        fi

        cp -r "$skill_dir" "$dest"
        installed=$((installed + 1))
    fi
done

echo ""
echo "Done. $installed skill(s) installed to $SKILLS_DEST"
echo ""
echo "Trigger the pipeline in any Claude Code session:"

# Design Standards

auto-spicy-github separates **craft rules** (universal, baked in) from **brand identity** (yours, pluggable).

## What's baked in

The `visual-output-standards` skill enforces technical correctness that applies to every SVG regardless of aesthetic:

- Font size minimums (14px for chart labels, 12px for footnotes)
- Paint order (backgrounds → geometry → strokes → text — always)
- Text container margin rules (25% beyond estimated width)
- ASCII-only SVG text (Unicode glyphs render inconsistently)
- Polygon geometry from stated center points
- WCAG AA contrast (4.5:1 on all text)
- Post-creation verification checklist

These rules catch the most common classes of visual failure. They don't care what your brand looks like — they make sure SVGs render correctly.

## What you bring

Your `docs/assets/VISUAL-IDENTITY.md` defines:

- Your palette (background, text, accent colors)
- Typography choices
- Visual personality and imagery style
